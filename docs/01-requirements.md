## 1. 專案概述

### 1.1 背景

台灣小吃店（滷肉飯、麵線、鹽酥雞、蚵仔煎……）的外帶與外送仍高度依賴電話與臨櫃點餐，常見痛點：

- 尖峰時段電話佔線、口頭點餐容易出錯（「小辣、不要香菜、加滷蛋」）。
- 顧客不知道要等多久，也無法預約取餐時間。
- 小吃店人力有限，導入系統必須**低門檻、手機優先、不需下載 App**。

### 1.2 目標

1. 消費者用手機瀏覽器即可完成「看菜單 → 客製化 → 結帳 → 追蹤取餐」，**不需註冊**。
2. 在沒有後端的情況下，提供**可直接部署、可完整操作**的 Demo，用於需求驗證、客戶展示與使用者測試。
3. 以「資料契約先行」設計：Mock 與正式 API 共用同一份介面，串接 API 時 UI 層不需改動。
4. **免登入、業態中立**：顧客不需註冊或登入即可完成「瀏覽 → 點餐 → 付款 → 追蹤」；介面採白底簡約與可換品牌色，可套用於不同餐飲業，且在商品缺少圖片或選項資料時仍完整可用。
5. **人人可用、回訪更快**：支援無障礙（WCAG 2.2 AA）、觸控面板裝置與純鍵盤操作，並提供可選用的單一小寫字母快速鍵加速（預設關閉；偵測到實體鍵盤時以不影響版面的方式提醒可開啟，開啟後附可見提示）；回訪者以「上次點過的選項」一鍵再點。
6. **送出時不超賣、被退回可就地恢復**：限量商品與預約時段以「送出訂單」的單一交易為唯一最終確認；被庫存或時段異動退回時，留在結帳頁一次列出全部異動並就地處理，不需重填（BR-38～41）。

## 2. 範圍

### 2.1 階段規劃

| 階段 | 名稱 | 內容 | 資料來源 |
| --- | --- | --- | --- |
| P1 | 純前端 Demo | 本文件 **M、S** 級需求；含 Demo 工具（模擬店家、時間穿梭） | Mock + localStorage |
| P2 | 串接 API 上線 | 對接真實後端、金流、電子發票、簡訊；**C** 級需求（點數、評價、PWA 等） | HTTP API |
| P3 | 平台化 | 多分店 / 多商家、LINE 登入、店家後台整合、外送平台整合 | HTTP API |

### 2.2 範圍內（In Scope）

- 消費者端：菜單瀏覽、商品客製化、購物車、結帳、付款（Demo 為模擬）、訂單追蹤、會員中心。
- 取餐方式：**自取**、**外送**、**內用（可掃描桌上 QR Code 帶入桌號，也可直接選「內用」；桌號選填，沒有桌號以取餐號碼叫號）**。
- 免登入點餐：訪客可完成全部點餐流程；會員僅提供加速與保存（地址簿、歷史、最愛、會員券）。
- 視覺與資料降級：白底簡約介面、可換品牌主題色、圖卡 / 清單兩種菜單版面；商品缺少圖片、描述或選項時優雅降級。
- 無障礙與多輸入裝置：WCAG 2.2 AA、純鍵盤操作與可選用的單一小寫字母快速鍵（預設關閉；偵測到實體鍵盤時提醒可開啟，開啟後附可見提示與說明）、螢幕閱讀器、觸控面板（含 Kiosk 模式）。
- 點餐記憶：記住每個商品上次點過的選項，提供一鍵再點、「常點」區塊與面板預設套用。
- 庫存與時段最終確認：限量商品與預約時段於送出訂單的單一交易內重新驗證並同時計入（全有或全無）；被退回時留在結帳頁，以異動清單一次列出全部異動並就地處理；結果未知時以同一把 `Idempotency-Key` 重送，不重複建立（BR-38～41）。
- 台灣在地需求：手機號碼 + OTP 登入（選填）、電子發票載具 / 統編 / 捐贈、行政區外送範圍、營業時段與公休日、取餐號碼、自備餐具。
- Demo 專屬功能：模擬店家接單、時間穿梭、付款結果模擬、庫存與時段情境、送出結果模擬、鍵盤提醒重播、資料重置。

### 2.3 範圍外（Out of Scope）

| 項目 | 說明 |
| --- | --- |
| 店家後台 / POS / KDS | Phase 1 以 Demo 模擬器取代；Phase 3 另立專案 |
| 外送員 App / 派單 | 僅呈現「外送中」狀態 |
| 真實金流、電子發票、簡訊 | Phase 1 全部模擬；Phase 2 由後端整合 |

## 3. 使用者角色

| 角色 | 說明 | 主要行為 |
| --- | --- | --- |
| 訪客（Guest） | 未登入的消費者 | 瀏覽菜單、加入購物車、訪客結帳、以「訂單編號 + 手機」查詢訂單 |
| 會員（Member） | 以手機 + OTP 登入 | 訪客全部功能 + 歷史訂單、地址簿、我的最愛、優惠券、再來一單 |
| 店家（Store） | 店員 / 老闆 | 不在 Phase 1 UI 範圍；由 Demo 模擬器代行接單、出餐、完成 |
| 系統（System） | 排程與自動規則 | 付款逾時取消、店家未接單逾時取消（取消即釋放庫存與時段）、訂單編號產生 |
| Demo 操作者 | 展示與測試人員 | 使用 Demo 工具面板切換情境（PG-18） |

## 4. 名詞定義

| 名詞 | 定義 |
| --- | --- |
| 自取（PICKUP） | 顧客到店取餐 |
| 外送（DELIVERY） | 店家（或其合作外送員）送達顧客地址 |
| 內用（DINE_IN） | 顧客在店內用餐點餐：可掃描桌上 QR Code 帶入桌號，也可直接選「內用」；桌號選填（自由入座、先領餐號叫號時可以沒有桌號） |
| 即時單（ASAP） | 「盡快」取餐/送達，無指定時段 |
| 預約單（Scheduled） | 指定未來某時段取餐/送達 |
| 取餐號碼（pickup_no） | 店內叫號用的當日流水號，例：`A027`（A=自取、D=外送、T=內用） |
| 桌號（table_no） | 內用單選填的桌位識別，例：`A3`；有提供時須為店家桌位（VR-10）。沒有桌號的內用單，以 `T` 前綴的取餐號碼叫號與領餐（BR-22） |
| 訂單編號（order_no） | 全域唯一，例：`ZO261014K7M3QX`，供查詢與客服 |
| 客製化選項 | 商品的規格、辣度、加料、甜度冰塊等，分為「選項群組」與「選項」 |
| 售完 | 當日該商品無法再點（手動標示，或可購買份數為 0） |
| 暫停接單 | 店家因忙碌手動暫停，即使在營業時間內也無法下單 |
| 保留 | 訂單建立（線上付款為 `PENDING_PAYMENT`、現金為 `PENDING`）起即計入已售份數與時段已訂數，直到訂單取消、拒單、付款逾時或接單逾時才釋放；購物車與 `quote` 不保留（BR-38） |
| 可購買份數 | 取餐營業日的 `daily_limit` 減去計入集合內該商品份數加總，不得為負；不限量商品無此值（BR-38、BR-40） |
| 異動清單 | 結帳時一次列出無法依原內容成立之項目（售完、下架、選項失效、數量不足、時段額滿或取餐方式不可用、折扣 / 付款 / 發票 / 外送條件，以及固定列在最後的價格更新）並提供就地處理的面板（CMP-40） |
| 結果未知 | 送出訂單後無回應、逾時或 5xx，無法確認訂單是否已建立；以同一把 `Idempotency-Key` 重送可安全取得結果（BR-41） |
| 鍵盤提醒 | 偵測到實體鍵盤後，提示可開啟單鍵快速鍵的非阻擋浮動提醒（CMP-41）；不位移版面，按「開啟」才寫入偏好（BR-42） |
| 載具 | 電子發票的歸戶方式：手機條碼、自然人憑證條碼 |
| 愛心碼 | 捐贈發票的受贈單位代碼（3～7 碼數字） |
| 統編 | 統一編號，8 碼，開立公司戶發票用 |
| 時間穿梭 | Demo 功能：模擬「現在時間」以展示不同營業狀態 |

## 5. 功能需求

### 5.0 編號與優先級

- 編號：`FR-<模組>-<流水號>`，模組代碼：ST 店家、MN 菜單、PD 商品客製化、CT 購物車、CK 結帳、PY 付款、OD 訂單、AC 會員、PR 優惠、DM Demo、SY 系統。
- 優先級：

| 級別 | 意義 | 階段 |
| --- | --- | --- |
| **M** Must | 必須完成，缺少則 Demo 流程不完整（Release gate） | P1 |
| **S** Should | 應該完成，缺少不阻擋 Demo 但影響完整度 | P1 |
| **C** Could | 加分項，或明確延後至正式上線階段 | P2+ |

- 驗收標準寫法：可直接轉為測試案例，細部情境見 [§11 UAT](#11-驗收情境uat)。

**統一編號檢查碼（VR-11）**：各位數依權重 `1,2,1,2,1,2,4,1` 相乘，乘積的十位數與個位數相加後加總為 `S`。`S` 能被 5 整除即合法；若第 7 碼為 `7`，則 `S` 或 `S+1` 能被 5 整除皆合法。（2023/04/01 起除數由 10 改為 5，採用 5 可同時相容新舊統編；依財政部公告，實作前請查證最新規定。）

```ts
export function isValidTaxId(id: string): boolean {
  if (!/^\d{8}$/.test(id)) return false;
  const weights = [1, 2, 1, 2, 1, 2, 4, 1];
  let sum = 0;
  for (let i = 0; i < 8; i++) {
    const p = Number(id[i]) * (weights[i] ?? 0);
    sum += Math.floor(p / 10) + (p % 10);
  }
  return sum % 5 === 0 || (id[6] === '7' && (sum + 1) % 5 === 0);
}
```

> 實作位置：`src/domain/validation.ts`（見 [07 §9](./07-frontend-architecture.md)）；表單、Mock 後端與測試共用同一份。

| EC-38 | 預約隔營業日，或店家調降限量低於已售 | 預約隔營業日的單只消耗該營業日限量，今日手動售完旗標不擋明日（Q-12）；加入購物車仍以今日剩餘保守封頂；選定隔日時段後，庫存文案的「今日」依取餐營業日改為「明天（M/D）」（文案見 03 §9）；店家調降 `daily_limit` 低於已售時剩餘夾為 0、不得為負，既有訂單不受影響（BR-40；僅以契約測試驗證，不另列 UAT：07 §13 庫存-18、庫存-19） |
| EC-39 | 軟鍵盤、輸入法組字、自動填入或輔助科技（螢幕閱讀器瀏覽模式、語音控制）產生按鍵事件 | 不誤判為實體鍵盤：合成（`isTrusted=false`）、組字中與無實體 `code` 的事件不計為證據，輸入元件內的打字不算證據（Tab 例外，視為導覽證據）；純觸控裝置需更高門檻（BR-42）；螢幕閱讀器瀏覽模式吃掉字母鍵與方向鍵時不會被提醒；焦點模式下最多提醒一次並以 polite 通報；偵測結果不隱藏或停用任何輸入方式（BR-36） |
| EC-40 | 提醒顯示或待命時遇到 Toast、商品面板、對話框、閒置警示、Demo 面板，或取得焦點的元素位於提醒下方 | Toast 與浮層優先：待命中不顯示，已顯示的提醒被搶走即轉為本次載入不再出現，不與 Toast 上下堆疊；不在結帳與付款路由出現；取得焦點的元素位於卡片下方時，待命中維持不顯示，已顯示時於焦點進入被遮住的元素當下收起，不遮住取得焦點的元素（WCAG 2.4.11），卡片可暫時覆蓋非互動的標題區；Esc 依序：關閉最上層浮層 → 收起提醒（可見且焦點在其中時）→ 清除搜尋（BR-34） |

| EC-42 | 內用沒有桌號（自由入座、先領餐號叫號）；或 `?table=` 的 QR 桌號無法辨識、店家未開放內用 | 桌號選填（BR-22）：結帳選「內用」並留空可正常送出，請求不帶 `dineIn.tableNo`，仍產生 `T` 前綴的取餐號碼；訂單頁沒有桌號時**不顯示**「桌號」列（不出現「桌號 undefined」或空白列），取餐資訊列改為「內用・{店名}・取餐號碼 T001」（例：「內用・巷仔內小吃部・取餐號碼 T001」；頁面標題為「訂單追蹤・T001」）；歷史訂單、查詢結果與 Demo 面板本來就只列取餐方式與取餐號碼，不含桌號。有提供桌號但不是店家桌位 → `422 TABLE_NOT_FOUND`，定位到桌號欄，可改正或留空。QR 桌號無法辨識或店家未開放內用時，非阻擋提示並回退為一般點餐（行為不變），文案提示「要內用請改選「內用」（桌號可留空）」。觸控面板沒有桌號欄，內用單一律無桌號（BR-36） |

### 10.2 風險

| 編號 | 風險 | 影響 | 對策 |
| --- | --- | --- | --- |

| R-07 | 未付款或現金預約單長時間占用限量庫存（含惡意；免登入訪客可無成本建立） | 限量商品被佔住，其他顧客無法購買 | 線上付款 15 分鐘到期即釋放（惰性排除加排程）；現金預約單保留至接單期限（BR-17，自進入 `PENDING` 起算，最長可至預約時間前，BR-38）；`POST /orders` 專屬速率限制（同 IP 每分鐘 10 次、同手機 10 分鐘 5 次，見 [06 §1.6](./06-api-spec.md)）先行；待處理訂單上限列 Q-14（Phase 2 上線前須設定有限值）；對帳加入「逾接單期限仍待處理」的訂單數（含預約單） |
| R-08 | Mock 單執行緒無法暴露真實併發，串接後才發現超賣 | 上線後才出現超賣 | Mock 建單臨界區（Web Locks + 重讀 db）與同一組契約並行測試、屬性測試；後端提供測試輔助（可設定時鐘、他人下單）；Demo 指南如實說明 Mock 限制 |
